# 0002. DB 접근에 sync SQLAlchemy 사용

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

이 서비스는 AutoML 플랫폼의 모델 관리 API로, 모델(`models`)과 모델 버전(`model_versions`)의 생명주기를 관리한다.

- 모델 생성, 수정, 삭제는 고객이 가끔 수행하는 저빈도 작업이다.
- 요청 대부분은 짧은 DB 쿼리로 끝나며, 외부 서비스 호출처럼 오래 기다리는 I/O가 없다.
- 버전 번호 동시성 처리(`SELECT ... FOR NO KEY UPDATE`, [0003](0003-version-number-concurrency.md))와 유스케이스 단위 트랜잭션 경계가 핵심 요구사항이다. 잠금 범위와 커밋, 롤백 시점을 코드에서 명확하게 읽을 수 있어야 한다.

FastAPI는 sync와 async를 모두 지원하므로, DB 접근 계층의 동시성 모델을 먼저 정해야 한다.

### 규모 가정

동시성 모델과 DB 연결 전략은 서비스 규모에 따라 달라지므로, 아래 규모를 가정하고 결정했다. 표의 값은 모두 실측이 아닌 가정이다.

| 항목 | 가정 |
|---|---|
| 운영 조직 | 소규모 엔지니어링 팀이 플랫폼 전체를 운영한다 |
| 고객 구성 | 산업 현장 장비를 운영하는 기업 고객(B2B) |
| 운영 지역 | 여러 국가의 고객이 같은 플랫폼을 쓴다 |
| 고객사 수 | 수십-수백 곳 |
| 트래픽 성격 | 현장 장비 단위의 추론 트래픽은 많고, 모델 관리는 저빈도 |

이 가정은 운영 지표(고객사 수, 요청 수, DB 연결 수)가 쌓이면 실측값으로 바꾼다.

## 결정

- SQLAlchemy 2.0 sync 세션과 psycopg 3 드라이버(`postgresql+psycopg`)를 사용한다.
- 엔드포인트는 `def`로 선언하고 FastAPI 스레드풀에서 실행한다.
- 세션은 요청마다 의존성(`app/api/deps.py`)으로 만들고, 트랜잭션은 service 계층에서 유스케이스 단위로 시작하고 끝낸다.

## 검토한 대안

### async SQLAlchemy + asyncpg

- 장점
  - 이벤트 루프 하나로 많은 동시 요청을 처리할 수 있어, 프로세스 하나가 감당하는 동시 요청 수가 많고 메모리 효율이 좋다.
- 단점
  - 관계를 지연 로딩하면 `MissingGreenlet` 오류가 날 수 있다. 모든 조회에 eager loading을 강제해야 하고, 실수는 런타임에야 드러난다.
  - 트랜잭션 코드와 테스트 코드가 복잡해진다(async 픽스처, 이벤트 루프 범위 관리, `await`가 빠지는 실수).
- 이 서비스에서는 요청 처리 시간 대부분이 DB 응답 시간이다. async로 바꿔도 DB가 처리할 수 있는 양은 그대로이므로 처리량 이득이 작다.

## 결과

### 트레이드오프

- 동시 요청 수는 스레드풀 크기(기본 40)로 제한된다. 저빈도 관리 API에서는 충분하다.
- 스레드마다 메모리를 쓰므로 Pod 하나의 효율은 async보다 낮다.
- 스레드풀(40)이 커넥션 풀(최대 10)보다 크므로, 요청이 몰리면 스레드가 커넥션을 기다린다. 무한히 기다리지 않도록 아래 연결 예산의 `pool_timeout`으로 빠르게 실패시킨다.

### DB 연결 예산

Pod 수를 늘리면 DB 연결 수도 함께 늘어난다. 예를 들어 Pod당 `pool_size=10, max_overflow=10`이면 Pod 10개에서 최대 200개가 되어 PostgreSQL 기본 `max_connections`(100)를 넘는다. 그래서 Pod당 연결 수를 작게 고정하고, 전체 연결 수는 공식으로 관리한다.

- 프로세스: Pod당 uvicorn 워커 1개. 확장은 워커 수가 아니라 Pod 단위(HPA)로 한다. 워커를 늘리면 Pod 하나의 연결 수가 워커 수만큼 곱해져 예산을 계산하기 어렵다.
- 커넥션 풀: `pool_size=5`, `max_overflow=5` (Pod당 최대 10). 환경 변수(`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT`)로 조정할 수 있다.
- 연결 예산 공식: `HPA 최대 Pod 수 × Pod당 최대 연결 수 + 운영 작업 여유 ≤ DB가 받을 수 있는 연결 수`
  - 운영 작업 여유는 마이그레이션 Job, 영구 삭제 CronJob, 모니터링, 관리자 접속에 쓰는 연결이다. 약 15개로 잡는다.
  - 위 규모 가정에서 관리 API는 Pod 2–3개면 충분하다. 3 × 10 + 15 = 45로, PostgreSQL 기본 `max_connections`(100) 안에 들어온다. 따라서 **지금은 PgBouncer 없이 DB에 직접 연결한다.**
  - 직접 연결로 감당할 수 있는 상한은 HPA 최대 Pod 8개(8 × 10 + 15 = 95)다.
- 대기 제한: `pool_timeout=5`초. 커넥션을 5초 안에 얻지 못하면 503 `SERVICE_UNAVAILABLE`과 `Retry-After` 헤더를 반환해 빠르게 실패한다. 요청이 쌓여 스레드풀 전체가 막히는 것보다, 클라이언트나 게이트웨이가 재시도하게 하는 편이 낫다.

### 확장 전략

트래픽이 늘면 서버 한 대의 효율을 높이기보다 수평 확장으로 대응한다. 운영할 구성 요소를 늘리는 일은 소규모 팀에 부담이 되므로, 각 단계는 지표가 기준을 넘을 때만 도입한다.

| 단계 | 도입 조건 | 대응 |
|---|---|---|
| 1. 직접 연결 (현재) | 연결 예산이 `max_connections` 안에 들어옴 | Kubernetes HPA로 API Pod를 늘린다 (최대 8개) |
| 2. 커넥션 풀러 | HPA 최대 Pod 수가 8개를 넘어야 하거나, 다른 서비스가 같은 DB를 쓰기 시작함 | PgBouncer(트랜잭션 모드)를 앞에 둔다. 공식의 우변은 PgBouncer `max_client_conn`이 되고, 실제 DB 연결은 PgBouncer 풀 크기만큼만 생긴다 |
| 3. 읽기 분산 | DB CPU의 대부분을 읽기 쿼리가 차지함 | Read Replica를 두고 목록, 단건 조회를 분산한다 |

2단계 도입 시 주의할 점: psycopg 3는 같은 쿼리를 여러 번 실행하면 자동으로 prepared statement를 만든다(`prepare_threshold`, 기본 5회). PgBouncer 트랜잭션 모드에서는 트랜잭션마다 실제 DB 연결이 바뀔 수 있어 충돌할 수 있다. 다음 중 하나로 대응한다.

- PgBouncer 1.21 이상을 쓰고 `max_prepared_statements`를 켠다.
- 드라이버 연결 옵션에 `prepare_threshold=None`을 지정해 자동 prepared statement를 끈다.

이 단계들은 sync/async 선택과 관계없다. 실제 병목은 DB 연결 수이기 때문이다.

트래픽이 몰리고 모델 서버 응답을 오래 기다리는 추론 게이트웨이는 async로 설계한다. 서비스 특성에 따라 동시성 모델을 다르게 고른다.

| 서비스 | 트래픽 | 대기 시간 | 선택 |
|---|---|---|---|
| 모델 관리 API | 낮음 | 짧음 (DB 쿼리) | sync |
| 추론 게이트웨이 | 높음 | 김 (모델 서버 응답) | async |

### 이후 전환 경로

psycopg 3는 sync와 async를 모두 지원한다. async 전환이 필요해지면 드라이버는 그대로 두고 세션 계층(`app/db/session.py`, `app/api/deps.py`)과 service 계층의 호출 방식만 바꿔 옮길 수 있다.
