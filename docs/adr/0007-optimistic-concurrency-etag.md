# 0007. ETag와 If-Match로 모델 동시 수정 방지

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

- 모델은 조직이 소유하고, 같은 조직의 여러 사용자가 같은 모델을 다룬다([0006](0006-organization-ownership.md)).
- 모델 행 잠금([0003](0003-version-number-concurrency.md))은 쓰기 요청을 하나씩 실행되게 할 뿐, **사용자가 낡은 화면을 보고 수정하는 문제**는 막지 못한다.
  - 예: A와 B가 같은 모델 화면을 연다. A가 설명을 고쳐 저장한다. B는 A의 수정을 보지 못한 채 이름만 고쳐 저장하는데, 화면에 남아 있던 이전 설명도 함께 보낸다. 결과적으로 A의 수정이 사라진다(lost update).
  - 예: B가 "버전 없음" 화면을 보고 `task_type`을 바꾸려는 사이, 학습 파이프라인이 첫 버전을 만든다. B는 바뀐 상황을 모른다.
- 기업 고객의 모델은 운영 중인 설비 제어와 연결되므로, 의도하지 않은 덮어쓰기는 조용히 넘기면 안 된다.

## 결정

### 버전 카운터

- `models.row_version`(정수, 기본값 1) 컬럼을 둔다.
- 모델 단건 응답의 내용이 바뀌는 모든 쓰기에서 1씩 올린다: 수정, 삭제, 복원, 버전 생성, 버전 상태 변경.
  - 버전 생성과 상태 변경도 올리는 이유는 단건 응답에 버전 목록과 상태가 들어 있기 때문이다. 두 번째 예처럼 버전이 생긴 사실도 "모델이 바뀌었다"로 감지된다.
- 이 작업들은 모두 모델 행을 `FOR NO KEY UPDATE`로 잠그므로, 같은 잠금 안에서 증가시키면 경쟁 없이 정확하다.

### ETag와 If-Match

- 모델 단건 응답(생성, 조회, 수정, 복원)에 `ETag: "<row_version>"`을 붙인다. 내용이 바뀔 때마다 값이 바뀌므로 strong ETag로 쓴다.
- 수정(PATCH), 삭제(DELETE), 복원(POST restore)은 `If-Match` 헤더를 **선택적으로** 받는다.
  - 있으면: 모델 행을 잠근 뒤 현재 ETag와 비교한다. 다르면 412 `PRECONDITION_FAILED`를 반환하고, 응답에 현재 `ETag`를 넣어 클라이언트가 다시 조회하고 재시도할 수 있게 한다.
  - 없으면: 비교 없이 처리한다(마지막 쓰기 우선).
  - `*`는 모델이 존재하면 통과한다.
  - RFC 9110의 `If-Match` 비교는 strong 비교이므로, 약한 ETag(`W/"..."`)는 일치하지 않는 것으로 본다.
- 웹 클라이언트는 항상 `If-Match`를 보내도록 구현한다. 서버는 선택으로 두어 Swagger, curl, 단순한 스크립트도 바로 쓸 수 있게 한다.

## 검토한 대안

### If-Match 필수 (없으면 428 Precondition Required)

- 장점: 덮어쓰기를 확실히 막는다.
- 단점: 모든 수정 전에 GET으로 ETag를 받아야 해서 Swagger, curl, 자동화 스크립트에서 쓰기 번거롭다.
- 고객사 담당자가 쓰는 웹 화면에서는 클라이언트가 항상 보내므로, 선택으로 두어도 주요 경로는 보호된다. 사고가 확인되면 필수로 바꿀 수 있다.

### `updated_at`을 ETag로 사용

- 장점: 컬럼을 추가하지 않는다.
- 단점: 시각 정밀도와 시계에 의존한다. 버전 생성처럼 모델 컬럼은 그대로인데 응답이 바뀌는 경우에도 `updated_at`을 일부러 바꿔야 해서 의미가 흐려진다.

### SQLAlchemy `version_id_col`

- 장점: ORM이 `UPDATE ... WHERE row_version = :old`를 자동으로 만들어 준다.
- 단점: 이미 모델 행을 잠근 뒤 비교하므로 추가 이득이 없다. 버전 생성과 상태 변경처럼 모델 컬럼을 바꾸지 않는 쓰기에서 카운터를 올리는 규칙을 명시적으로 다루기 어렵다.

### 응답 본문 해시를 ETag로 사용

- 장점: 응답 내용과 ETag가 정확히 일치한다.
- 단점: 비교할 때마다 현재 응답을 만들어 해시를 계산해야 한다. 정수 카운터로 같은 목적을 이룰 수 있다.

## 결과

- 낡은 화면에서 보낸 수정, 삭제, 복원은 412로 거부되어 다른 사람의 수정이 조용히 사라지지 않는다.
- 클라이언트는 412를 받으면 다시 조회하고, 사용자에게 바뀐 내용을 보여준 뒤 재시도한다.
- 트레이드오프
  - 모든 쓰기 경로가 `row_version` 증가를 빠뜨리지 않아야 한다. 증가는 service 계층의 모델 행 잠금 함수 한 곳에서 하고, 쓰기 유스케이스마다 ETag가 바뀌는지 통합 테스트로 확인한다.
  - `If-Match`가 선택이므로 이를 보내지 않는 클라이언트는 여전히 마지막 쓰기 우선이다.
