# 0008. 에러 응답 형식과 에러 코드 카탈로그

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

- 이 API는 웹 클라이언트, 다른 내부 서비스, Swagger와 curl 같은 도구가 함께 호출한다. 고객은 여러 국가에 있고, 클라이언트가 에러 문구를 각 언어로 현지화한다.
- 클라이언트는 에러를 HTTP 상태만으로 구분할 수 없다. 예를 들어 409 하나에 "같은 이름의 모델이 있음"과 "버전이 있어 유형을 바꿀 수 없음"이라는 서로 다른 의미가 있고, 화면에서 안내할 내용도 다르다.
- FastAPI 기본 에러 형식은 경우마다 모양이 다르다. 직접 낸 에러는 `{"detail": "문자열"}`, 검증 오류(422)는 `{"detail": [ ... ]}`이고, 검증 오류에는 요청 값(`input`)이 그대로 되돌아가 개인정보가 섞일 수 있다.
- 에러 코드, HTTP 상태, 발생 조건이 코드 곳곳에 흩어지면 OpenAPI 문서와 README 표가 실제 동작과 어긋나기 쉽다.

## 결정

### 응답 형식

모든 에러는 같은 형식으로 응답한다.

```json
{"error": {"code": "MODEL_NAME_CONFLICT", "message": "An active model with the same name already exists in the organization.", "details": null}}
```

- `code`: 클라이언트가 분기에 쓰는 안정적인 식별자. 한 번 정하면 바꾸지 않는다.
- `message`: 개발자가 로그와 응답을 읽기 위한 영어 한 문장. 화면에 그대로 보여주지 않으며, 클라이언트는 이 값을 파싱하지 않는다.
- `details`: 추가 정보. 검증 오류는 `[{"location": ["body", "name"], "message": "...", "type": "..."}]` 목록이며, 요청 값(`input`)은 넣지 않는다.
- 요청 ID는 본문이 아니라 모든 응답의 `X-Request-ID` 헤더로 전달한다. 성공과 실패 응답에서 같은 방식으로 찾을 수 있게 하기 위해서다.

### 에러 코드 카탈로그

- `app/core/errors.py`의 카탈로그 한 곳에서 코드별 HTTP 상태, 발생 조건, 기본 메시지를 정한다.
- 서비스 계층은 HTTP를 모른 채 `AppError(ErrorCode.MODEL_NOT_FOUND)`처럼 코드로만 실패를 알린다. 전역 핸들러가 카탈로그를 보고 HTTP 상태와 본문을 만든다.
- OpenAPI 문서는 엔드포인트마다 낼 수 있는 코드 목록을 받아 카탈로그로부터 만든다. 같은 상태의 코드는 한 응답 아래 예시로 묶는다.
- README의 에러 코드 표도 이 카탈로그를 기준으로 작성한다.

### 적용 범위

- 도메인 예외뿐 아니라 프레임워크가 내는 에러도 같은 형식으로 바꾼다: 요청 검증(422 `VALIDATION_ERROR`), 정의되지 않은 경로(404 `NOT_FOUND`), 허용되지 않은 메서드(405 `METHOD_NOT_ALLOWED`), DB 장애(503 `SERVICE_UNAVAILABLE`).
- 처리되지 않은 예외(500 `INTERNAL_ERROR`)는 요청 ID 미들웨어가 같은 형식으로 응답한다. 내부 정보는 응답에 넣지 않고 로그로만 남긴다.

## 검토한 대안

### RFC 9457 Problem Details (`application/problem+json`)

- 장점: HTTP API 에러의 IETF 표준이다. `type`, `title`, `status`, `detail`, `instance` 필드가 정해져 있고, 이를 이해하는 도구와 라이브러리가 있다.
- 단점
  - 에러 종류를 `type` URI로 구분하므로, 문서 URL을 정하고 운영해야 하며 클라이언트는 URI 문자열로 분기한다.
  - `title`, `detail`이 사람이 읽는 문장이라, 현지화를 클라이언트가 맡는 지금 구조에서는 `message`와 역할이 겹친다.
  - 검증 오류 목록 같은 정보는 어차피 확장 필드로 정의해야 한다.
- 지금 클라이언트는 사내 웹과 내부 서비스뿐이라 표준 도구와의 호환보다 단순한 코드 분기가 더 중요하다고 판단했다.
- 외부 개발자에게 API를 공개하게 되면, `code`를 확장 필드로 유지한 채 Problem Details 형식을 함께 제공하는 방식으로 옮길 수 있다.

### FastAPI 기본 형식 유지

- 장점: 추가 코드가 없다.
- 단점: 경우마다 모양이 다르고, 에러 종류를 구분할 코드가 없으며, 검증 오류에 요청 값이 그대로 되돌아간다.

### HTTP 상태만으로 구분

- 장점: 가장 단순하다.
- 단점: 같은 상태 안의 서로 다른 의미(409 이름 충돌과 유형 잠금, 404 경로 없음과 모델 없음)를 클라이언트가 구분할 수 없다.

### 도메인 예외를 상태별 클래스(`NotFound`, `Conflict` 등)로 나누기

- 장점: 예외 이름만 보고 HTTP 상태를 알 수 있다.
- 단점: 상태는 클래스에, 코드는 인자에 있어 `NotFound(ErrorCode.MODEL_NAME_CONFLICT)` 같은 잘못된 조합을 막을 수 없다. 상태와 코드를 카탈로그 한 곳에 두면 이런 불일치가 생기지 않는다.

## 결과

- 클라이언트는 `code` 하나로 분기하고 화면 문구를 현지화한다. 같은 상태 안의 서로 다른 에러도 구분할 수 있다.
- 새 에러를 추가할 때는 카탈로그에 한 줄을 넣고, 엔드포인트의 `responses`에 코드를 적고, README 표를 고친다. 카탈로그 누락은 테스트가 잡는다.
- 트레이드오프
  - 표준이 아닌 자체 형식이므로, 이 API를 처음 쓰는 개발자는 형식을 문서에서 확인해야 한다. OpenAPI의 에러 응답 예시와 README 표로 보완한다.
  - `code`는 한 번 공개하면 바꿀 수 없는 계약이다. 이름을 신중하게 정하고, 의미가 바뀌면 새 코드를 만든다.
