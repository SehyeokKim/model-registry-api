# 0009. 모델 소프트 삭제와 복원 기한

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

- 모델에는 학습에 쓴 GPU 시간과 그 결과물(버전, 아티팩트)이 묶여 있다. 실수로 삭제하면 다시 만드는 데 큰 비용이 든다. 같은 조직의 여러 사용자가 모델을 공유하므로([0006](0006-organization-ownership.md)), 다른 사람이 지운 모델을 되살려야 하는 경우도 생긴다.
- 반대로 고객이 삭제한 데이터를 언제까지나 보관할 수는 없다. 기한이 지난 모델은 영구 삭제해야 한다([0005](0005-purge-expired-models.md)).
- 그래서 다음을 정해야 한다.
  - 삭제를 어떻게 표현할지
  - 삭제된 모델을 어떤 API에서 어떻게 다룰지
  - 복원 기한을 사용자에게 어떻게 알릴지
  - 기한이 지난 모델을 어떻게 볼지
- [0005](0005-purge-expired-models.md)는 영구 삭제 작업과, 복원과 영구 삭제가 겹칠 때의 처리를 다룬다. 이 문서는 그 앞 단계인 삭제와 복원의 규칙을 다룬다.

## 결정

### 삭제 표현

- 삭제는 행을 지우지 않고 `deleted_at`에 삭제 시각을, `purge_at`에 `deleted_at + MODEL_RESTORE_WINDOW_DAYS`(기본 30일)를 기록한다.
- 두 컬럼이 함께 NULL이거나 함께 값이 있어야 한다. CHECK 제약(`soft_delete_pair`, `purge_after_delete`)으로 DB가 보장한다.
- 버전(`model_versions`)은 그대로 두므로, 복원하면 버전 목록도 삭제 전과 같다.

### 복원 기한은 미리 알린다

- 삭제 응답은 `{"id", "deleted_at", "purge_at"}`이다. 클라이언트는 삭제 직후 "N일 후 영구 삭제" 같은 안내를 보여줄 수 있다.
- 목록 항목에도 `purge_at`을 담아, 휴지통 화면에서 남은 기간을 보여줄 수 있게 한다.

### 기한이 지난 모델은 삭제가 확정된 것이다

- `purge_at <= now()`인 모델은 영구 삭제 작업을 기다리는 행일 뿐, 고객에게는 이미 없는 모델이다.
  - 목록 조회는 `status=deleted`, `status=all` 어느 쪽에도 이 모델을 넣지 않는다. 휴지통에는 복원할 수 있는 모델만 보인다.
  - 복원 요청에는 410 `MODEL_PURGED`로 응답한다. 410 Gone은 "있었지만 의도적으로, 영구히 없어졌다"는 뜻이라 상태와 맞고, 클라이언트는 "복원 기한이 지났다"고 정확히 안내할 수 있다.
  - 행이 실제로 지워진 뒤에는 404 `MODEL_NOT_FOUND`다([0005](0005-purge-expired-models.md)). 클라이언트는 410과 404를 모두 "복원할 수 없음"으로 처리하면 된다.
- 기한이 지났는지는 목록 조회와 복원 모두 DB 시각 기준의 같은 조건(`purge_at <= now()`)으로 판단한다. 애플리케이션 서버마다 시계가 조금씩 달라도 판단은 하나로 맞는다.

### 삭제된 모델의 API 동작

| API | 삭제된 모델(기한 전) | 기한이 지난 모델 |
|---|---|---|
| 단건 조회, 수정, 삭제 | 404 `MODEL_NOT_FOUND` | 404 `MODEL_NOT_FOUND` |
| 목록 `status=active` | 제외 | 제외 |
| 목록 `status=deleted`, `status=all` | 포함 | 제외 |
| 복원 | 200 | 410 `MODEL_PURGED` |

- 단건 조회와 수정에서 삭제된 모델을 404로 처리하는 이유는 다음과 같다.
  - 삭제된 모델을 고칠 수 있으면 복원 전후의 상태를 설명하기 어려워진다.
  - 클라이언트가 응답마다 삭제 여부를 확인해야 한다.
  - 삭제된 모델은 휴지통 목록(`status=deleted`)에서 보고, 복원한 뒤에 다룬다.

### 이름 재사용과 복원 시 충돌

- 활성 모델 이름 중복 방지는 partial unique index `(organization_id, name) WHERE deleted_at IS NULL`이다. 삭제된 모델의 이름은 바로 다시 쓸 수 있다.
- 복원할 때 같은 이름의 활성 모델이 이미 있으면 409 `MODEL_NAME_CONFLICT`로 응답하고, 이름을 자동으로 바꾸지 않는다. 사용자가 기존 모델의 이름을 바꾸거나 삭제한 뒤 다시 복원한다.
- 중복은 미리 조회하지 않고 인덱스 위반으로 판단한다. 같은 이름의 삭제 모델 여러 개를 동시에 복원해도 하나만 성공한다.

### 복원 처리

- 복원은 한 트랜잭션에서 모델 행을 `FOR NO KEY UPDATE`로 잠근 뒤 판단한다([0003](0003-version-number-concurrency.md)).
- 판단 순서는 다음과 같다.
  1. 없음, 다른 조직 소유, 영구 삭제됨: 404
  2. 삭제되지 않은 모델: 409 `MODEL_NOT_DELETED`
  3. 기한이 지남: 410
  4. 그 외에는 복원하고, 이때 이름 충돌이 있으면 409
- 복원은 단건 응답을 바꾸므로 `row_version`을 올린다([0007](0007-optimistic-concurrency-etag.md)).

## 검토한 대안

### 하드 삭제 (즉시 행 삭제)

- 장점: 구현이 가장 단순하고, 삭제된 데이터가 남지 않는다.
- 단점: 실수로 지우면 되돌릴 수 없다. 학습 비용이 큰 모델에는 맞지 않는다.

### `is_deleted` 플래그 컬럼

- 장점: 조건이 단순하다.
- 단점: 언제 지웠는지, 언제까지 복원할 수 있는지를 담지 못해 결국 시각 컬럼이 따로 필요하다. 시각 컬럼 하나로 삭제 여부와 시점을 함께 표현할 수 있다.

### 삭제 시 아카이브 테이블로 이동

- 장점: 운영 테이블에는 활성 모델만 남아 조회 조건이 단순하다.
- 단점: 복원할 때 행을 다시 옮겨야 하고, 버전과의 FK 관계와 ID를 유지하기 어렵다. 같은 스키마를 두 벌 관리해야 한다.

### 기한이 지난 모델도 목록에 표시

- 장점: DB 상태를 그대로 보여주고, 조회 조건이 단순하다.
- 단점: 고객에게는 이미 삭제가 확정된 모델을 보여주게 된다. 휴지통에 복원할 수 없는 모델이 섞여 혼란을 준다.

### 복원 시 이름 자동 변경 (예: `churn-predictor (1)`)

- 장점: 복원이 항상 성공한다.
- 단점: 사용자가 모르는 사이 이름이 바뀐다. 이름은 다른 시스템이나 문서에서 모델을 가리키는 식별자로 쓰일 수 있으므로, 바꾸는 판단은 사용자에게 맡긴다.

## 결과

- 삭제 후 `MODEL_RESTORE_WINDOW_DAYS` 동안은 복원할 수 있고, 기한과 남은 기간을 클라이언트가 보여줄 수 있다.
- 고객 관점에서 기한이 지난 모델은 목록과 복원 모두에서 "없는 모델"로 일관되게 다뤄진다.
- 트레이드오프
  - 활성 모델을 다루는 모든 쿼리에 `deleted_at IS NULL` 조건이 필요하다. repository의 조회 함수가 기본값으로 이 조건을 넣고, 삭제된 모델은 `include_deleted=True`로 명시해야 다룰 수 있게 해 실수를 줄인다.
  - 기한이 지난 모델의 복원 응답은 영구 삭제 작업이 돌았는지에 따라 410이나 404가 된다.
  - 복원 기간 동안 삭제된 모델의 행과 아티팩트가 남아 저장 비용이 든다.
