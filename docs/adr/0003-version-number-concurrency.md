# 0003. 모델 버전 번호 동시성 제어

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

- 모델 버전 번호(`model_versions.version_no`)는 모델별로 1부터 빈틈없이 순차 증가해야 하며, 동시에 생성해도 중복되면 안 된다.
- 같은 모델에 버전 생성 요청이 동시에 들어오는 경우가 있다. 예를 들어 재학습 요청 버튼을 연달아 누르거나, 사용자 요청과 자동 재학습 파이프라인이 겹칠 수 있다.
- PostgreSQL 기본 격리 수준(READ COMMITTED)에서 단순히 `max(version_no) + 1`을 조회한 뒤 INSERT하면, 두 트랜잭션이 같은 최댓값을 읽고 같은 번호로 INSERT한다.
- 버전 생성은 모델 삭제, 복원과도 겹칠 수 있다. 삭제 중인 모델에 버전이 생기면 안 된다.

## 결정

버전 생성은 하나의 트랜잭션 안에서 다음 순서로 처리한다. 격리 수준은 READ COMMITTED를 유지한다.

1. 부모 모델 행을 `SELECT ... FOR NO KEY UPDATE`로 잠근다. 같은 쿼리에서 요청자 조직의 모델인지(`organization_id`)와 활성 상태(`deleted_at IS NULL`)도 확인한다.
2. `SELECT coalesce(max(version_no), 0) + 1 FROM model_versions WHERE model_id = :id`로 다음 번호를 구한다. `(model_id, version_no)` unique 인덱스를 사용하므로 버전 수가 늘어도 빠르다.
3. 새 버전을 INSERT하고 커밋한다.

- 같은 모델에 대한 버전 생성은 1번 잠금에서 직렬화된다. 앞 트랜잭션이 커밋한 뒤에 다음 트랜잭션이 최댓값을 읽으므로 번호가 중복되지 않는다.
- 잠금 모드는 `FOR UPDATE` 대신 `FOR NO KEY UPDATE`(SQLAlchemy `with_for_update(key_share=True)`)를 쓴다.
  - 모델의 키 컬럼은 바꾸지 않으므로 이 잠금으로 충분하다.
  - 다른 테이블이 이 모델을 FK로 참조하며 INSERT할 때 거는 `FOR KEY SHARE` 잠금과 충돌하지 않는다. 앞으로 `deployments` 같은 참조 테이블이 늘어나도 불필요하게 막히지 않는다.
  - 모델 수정(PATCH), 삭제, 복원, 버전 상태 변경도 같은 잠금 모드로 모델 행을 잠근다. 따라서 버전 생성과 이 작업들이 서로 직렬화된다. 이 잠금 안에서 `If-Match` 비교와 `row_version` 증가도 한다([0007](0007-optimistic-concurrency-etag.md)).
  - `task_type` 수정은 버전이 하나도 없을 때만 허용하며, 버전 존재 확인도 이 잠금 안에서 한다. 잠금이 없으면 "버전 없음"을 확인한 직후 다른 트랜잭션이 버전을 만들어, 버전이 있는 모델의 유형이 바뀔 수 있다.
- unique 제약 `uq_model_versions_model_id_version_no`를 최종 방어선으로 둔다. 예상하지 못한 경로로 위반이 생기면 트랜잭션을 롤백하고 409 `MODEL_VERSION_CONFLICT`를 반환해 클라이언트가 재시도하게 한다.
- 잠금을 잡은 트랜잭션 안에서는 외부 호출을 하지 않는다. 잠금 유지 시간을 DB 쿼리 시간으로 제한하기 위해서다.

## 검토한 대안

### 카운터 컬럼 (`models.latest_version_no`) + `UPDATE ... RETURNING`

- 장점: 문장 하나로 번호를 원자적으로 증가시키고, 최댓값 조회가 필요 없다.
- 단점: 버전 번호의 기준이 `model_versions`와 `models` 두 곳으로 나뉘는 비정규화가 생기고 ERD가 바뀐다. 잠금 범위는 행 잠금과 같아서 동시성 측면의 이득은 없다.

### SERIALIZABLE 격리 수준 + 재시도

- 장점: 애플리케이션이 잠금을 명시하지 않아도 DB가 충돌을 감지한다.
- 단점: 직렬화 실패(`40001`) 재시도 로직이 필요하고, 트랜잭션 안의 모든 쿼리가 영향을 받는다. 경합이 생기면 실패와 재시도가 반복된다.

### unique 제약만 두고 충돌 시 애플리케이션에서 재시도

- 장점: 잠금이 없다.
- 단점: 경합이 생기면 재시도가 반복되고, 재시도 횟수와 백오프를 관리해야 한다. 삭제와 동시에 실행되는 문제는 해결하지 못한다.

### PostgreSQL advisory lock (`pg_advisory_xact_lock(hash(model_id))`)

- 장점: 테이블 행과 무관하게 임의의 키로 직렬화할 수 있다.
- 단점: 잠글 행(모델)이 이미 있으므로 행 잠금보다 나은 점이 없다. 해시 키를 관리해야 하고, 삭제나 복원과의 직렬화를 따로 맞춰야 한다.

### DB 시퀀스

- 단점: 시퀀스는 전역이라 모델별 번호를 만들 수 없다. 롤백된 트랜잭션도 값을 소비하므로 번호에 빈틈이 생긴다.

## 결과

- 같은 모델의 버전 생성은 순서대로 처리되고, 번호는 빈틈과 중복 없이 증가한다. 롤백된 트랜잭션은 번호를 소비하지 않는다.
- 서로 다른 모델의 버전 생성끼리는 경합하지 않는다.
- 트레이드오프
  - 같은 모델에 대한 버전 생성, 수정, 삭제, 복원, 버전 상태 변경은 잠금 시간만큼 서로 대기한다. 버전 생성은 저빈도 작업이고 트랜잭션이 짧으므로 허용한다.
  - 다른 경로로 `model_versions`에 INSERT하는 코드도 같은 순서(모델 행 잠금 → 번호 계산)를 따라야 한다. 이 규칙은 service 계층의 단일 유스케이스에만 두어 지킨다.
- `version_no`는 사람이 읽는 표시용 번호다. 모델 아티팩트와 체크포인트의 저장 경로는 `version_no`가 아니라 UUID로만 만든다.
  - 예: `models/{model_id}/versions/{version_id}/`, `checkpoints/{training_job_id}/`
  - `version_no` 기반 경로(`models/{model_id}/v3/`)는 롤백된 생성이나 재시도된 학습이 같은 경로에 쓰면서 기존 아티팩트를 덮어쓸 위험이 있다.
- 검증: 같은 모델에 버전 생성 요청 N개를 여러 스레드에서 동시에 보내고, 결과 번호가 정확히 1부터 N까지인지 통합 테스트로 확인한다.
