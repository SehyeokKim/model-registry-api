# 0006. 모델 소유 단위를 고객 조직(테넌트)으로

- 상태: 채택됨
- 날짜: 2026-10-06

## 배경

- 고객은 제조, 에너지, 물류 분야 기업이다([0002](0002-sync-sqlalchemy.md)의 규모 가정). 한 고객사 안에서 여러 담당자가 같은 데이터셋과 모델을 함께 다룬다.
- 처음 설계에서는 모델을 사용자 개인이 소유했다(`models.owner_id → users`). 이 구조는 기업 고객에게 다음 문제를 일으킨다.
  - 담당자가 퇴사하거나 바뀌면 그 사람이 만든 모델에 아무도 접근할 수 없다.
  - 같은 회사 동료끼리 모델을 공유할 방법이 없다.
  - 모델 이름 중복 규칙이 회사가 아니라 개인 단위로 걸려, 한 회사 안에 같은 이름의 활성 모델이 여러 개 생길 수 있다.
  - 데이터 접근 권한, 계약, 과금, 데이터 파기([0005](0005-purge-expired-models.md))는 모두 회사 단위인데, 데이터 소유만 개인 단위라 서로 맞지 않는다.
- 내부 사용자(ML Engineer, 관리자)는 특정 고객사에 속하지 않는다. 이들은 고객 API가 아니라 별도의 분석 환경과 내부 API(학습 파이프라인용)로 데이터에 접근한다.
- 서비스 요구사항은 "한 명의 사용자가 여러 데이터셋과 모델을 만들고 관리한다"는 수준만 정하고, 조직이나 사용자 수는 정하지 않는다. 따라서 여러 조직과 여러 사용자가 함께 쓰는 구조를 전제로 설계한다. 조직 소유로 바꿔도 한 사용자가 여러 모델을 만들고 관리할 수 있다는 요구사항은 그대로 충족된다.

## 결정

### 스키마

- `organizations` 테이블을 추가한다. 고객사 하나가 조직 하나다.
- `users.organization_id`(nullable FK)를 추가한다.
  - 고객(`CUSTOMER`)은 반드시 조직 하나에 속하고, 내부 사용자(`ML_ENGINEER`, `ADMIN`)는 조직이 없다.
  - CHECK 제약 `(role = 'CUSTOMER') = (organization_id IS NOT NULL)`로 DB가 보장한다.
- `models`는 `owner_id` 대신 다음 두 컬럼을 갖는다.
  - `organization_id`: 소유 조직(NOT NULL FK)
  - `created_by`: 만든 사용자(NOT NULL FK). 감사용 기록이며 권한 판단에는 쓰지 않는다.
- 활성 모델 이름 중복 방지는 조직 단위다: partial unique `(organization_id, name) WHERE deleted_at IS NULL`
- 목록 조회 인덱스도 조직 기준이다: `(organization_id, created_at, id)`. 최신순 조회(`ORDER BY created_at DESC, id DESC`)는 이 인덱스를 역방향으로 읽는다.
- 이 저장소 범위 밖의 `datasets`도 ERD에서 같은 구조(`organization_id`, `created_by`)로 바꾼다.

### 접근 규칙

- 요청자는 `X-User-Id`로 식별하고, 그 사용자의 조직을 요청 범위로 삼는다.
- 같은 조직의 사용자는 조직의 모든 모델을 조회, 수정, 삭제, 복원할 수 있다. 조직 안의 역할 구분(관리자, 일반 사용자)은 이후에 검토한다.
- 다른 조직의 모델은 존재 여부를 드러내지 않도록 404 `MODEL_NOT_FOUND`로 응답한다.
- 조직이 없는 내부 사용자가 고객 API(`/api/v1`)를 호출하면 403 `FORBIDDEN`이다.
- 반대로 내부 API(`/internal/v1`, 버전 상태 변경)는 내부 사용자만 호출할 수 있고 고객은 403이다. 내부 API는 조직 범위 제한이 없다.
- 조직 범위 필터는 빠뜨리면 바로 데이터 유출로 이어진다. 그래서 repository 계층에서 조직 소유 테이블을 다루는 함수는 `organization_id`를 필수 인자로 받는다. 조직 조건 없이 모델을 조회하는 함수는 만들지 않는다.

### 사용자와 조직의 관계

- 사용자는 조직 하나에만 속한다(1:N).
- 대상 고객이 산업 현장의 기업이라 한 사람이 여러 고객사에 동시에 속하는 경우는 드물다고 판단했다.

## 검토한 대안

### 사용자 개인 소유 유지 (`owner_id → users`)

- 장점: 테이블이 하나 적고 접근 규칙이 단순하다.
- 단점: 배경에 쓴 문제(퇴사, 공유, 이름 범위, 회사 단위 정책과의 불일치)가 그대로 남는다. 나중에 조직 단위로 바꾸려면 데이터 이전이 필요하다.

### 사용자-조직 N:M (`organization_members`)

- 장점: 컨설턴트나 그룹사 담당자처럼 여러 조직에 속하는 사용자를 표현할 수 있고, 조직별 역할을 멤버십에 둘 수 있다.
- 단점: 요청마다 "어느 조직으로 요청하는지"를 따로 받아야 한다(헤더나 경로). 지금 고객 구성에서는 필요가 확인되지 않았다.
- 필요해지면 `users.organization_id`를 멤버십 테이블로 옮기는 방식으로 확장한다. 모델의 `organization_id`는 그대로 쓸 수 있다.

### 조직별 스키마 또는 조직별 DB 분리

- 장점: 격리 수준이 가장 높고, 고객별 백업과 삭제가 쉽다.
- 단점: 조직 수만큼 마이그레이션과 커넥션 풀을 관리해야 한다. 소규모 팀이 운영하기에는 부담이 크다.
- 강한 격리가 필요한 고객은 온프레미스나 전용 클러스터 배포로 대응한다.

### PostgreSQL Row Level Security

- 장점: 애플리케이션이 조직 조건을 빠뜨려도 DB가 막는다.
- 단점: 요청마다 세션 변수로 조직을 설정해야 하고, 커넥션 풀이나 PgBouncer 트랜잭션 모드와 함께 쓸 때 설정이 섞이지 않게 주의해야 한다. 디버깅도 어려워진다.
- 지금은 repository 필수 인자와 조직 격리 테스트로 막고, 고객 수나 규제 요구가 커지면 다층 방어로 추가한다.

## 결과

- 담당자가 바뀌어도 모델은 조직에 남고, 같은 조직 사용자끼리 바로 공유된다.
- 이름 중복, 접근 권한, 데이터 파기가 모두 조직이라는 같은 단위로 맞춰진다.
- 트레이드오프
  - 모든 조회와 변경에 조직 조건이 붙는다. 조직 격리 통합 테스트로 이를 검증한다. 다른 조직 사용자가 조회, 수정, 삭제, 복원, 버전 생성을 시도하면 모두 404여야 한다.
  - 시드 데이터는 조직 2개, 고객 3명(조직 A에 2명, 조직 B에 1명), 내부 사용자 1명이다. 조직 내 공유, 조직 간 격리, 내부 사용자 차단을 바로 확인할 수 있다.
  - 조직 내 역할, N:M 멤버십, RLS는 이후 필요가 확인되면 도입한다.
